# Lane mode: одна вежа, коридор, без лабіринту

## Context

Поточна гра (`main`/`ts-migration`) — TD з лабіринтом: гравець малює стіни, BFS
перераховує маршрут, башти ставляться будь-де на сітці. Це і є головний гак
поточної гри.

Обговорена нова концепція («lane mode») — **інша гра, той самий рушій малювання**:
одна нерухома вежа зліва з фіксованими сокетами, вороги йдуть прямою лінією
справа наліво, окрема маленька коробка загону з юнітами, яких малює гравець.
Немає стін, немає вільної розстановки башт, немає BFS.

Це не варіант рівня — це інші правила гри. Робимо **окремим паралельним
кодом**, без єдиної зміни в існуючих файлах лабіринту. Гілка `lane-mode`
(від `ts-migration`) саме для цього: якщо ідея не приживеться, видаляється
без слідів у робочій грі.

**Гарантія:** `src/model/grid.ts`, `src/model/flow.ts`, `src/game.ts`,
`src/controller/tools.ts`, `src/controller/hud.ts`, `src/controller/workshop.ts`
не редагуються. Жодного рядка.

## Нові файли

### `data/laneLevel.json`
Замінює `level.json` для цього режиму. Значно простіший — без сітки:
```json
{
  "lives": 10,
  "rows": 4,
  "towerAnchor": { "xFrac": 0.12 },
  "entryXFrac": 1.05,
  "squadCols": 2,
  "waves": [ /* та сама форма Wave з types.ts + "row": число або null = випадковий */ ]
}
```
`xFrac` — частка ширини екрана, не клітинки: вежа завжди на місці незалежно
від орієнтації. Ряди рівномірно ділять висоту ігрової зони; `y` ряду
рахується в `relayout()`, тому воно живе в `Layout`-похідних, не в даних.

### `src/model/lane.ts` — новий, чиста логіка (без Pixi)
Геометрія рядів окремо від усього іншого, бо це єдине, що треба тестувати
математично:
- `rowY(row, rows, layout): number` — центр ряду в світових одиницях
- `rowOf(y, rows, layout): number` — у якому ряду точка
- Вежа стоїть на **всіх рядах одразу** (вона висока), тому пропущений ворог
  на будь-якому ряду доходить до неї.

### `src/model/squad.ts` — новий, чиста логіка (без Pixi)
Союзник має **тип бою** — і мілішні, і ренжові:
```ts
type AllyKind = 'melee' | 'ranged';
interface Ally {
  id: number; kind: AllyKind; row: number;
  hp: number; maxHp: number;
  quality: number;      // з обведення, множить усі стати
  fadeAt: number;       // сек до зникнення; недбалий в'яне швидше
  x: number;            // позиція в світі
  // melee: блокує рух, б'є впритул
  dmg?: number; hitEvery?: number; cd?: number;
  // ranged: не блокує, стріляє — заводиться в combat.ts
  gun?: Gun;
}
```
- `addAlly(kind, row, quality)` — додає, якщо в **цьому ряду** є місце
  (`squadCols` на ряд); якщо повно — знімає найслабшого за `quality`
- `blockerAt(row, x)` — найправіший живий `melee` у ряду перед точкою `x`.
  Це і є та функція, через яку `laneGame` вирішує, чи ворог іде далі
- `tick(dt)` — в'янення й видалення
- Покривається `tools/selfcheck.js` так само, як `build.ts`/`economy.ts`:
  саме тут легко тихо зламати «повний ряд», «найслабший на заміну»,
  «блокувальник у правильному ряду».

### `src/laneGame.ts` — новий хаб
Копіює прийоми з `game.ts` (список вище), але:
- **одна вежа**, не `Map<id, Built>` — `createBuild(towerParts.parts, towerParts)`
  один раз при старті, якорена в `towerAnchor`
- вороги: `e.x -= speed*dt`, кожен зі своїм `row`, без `flow`/`grid`
- **`combat.ts` без змін обслуговує і вежу, і ренжових союзників.**
  `distOf: (e) => e.x` — чим менший `x`, тим ближче до вежі. Ренжовий
  союзник заводиться через `combat.add(allyId, ally.gun, rig, x, y)` —
  той самий виклик, що для вежі. Комбо/рикошет/сплеш працюють безплатно
- **мілішні — окремий цикл у `laneGame.update()`**, бо `combat.ts` не знає
  про блокування руху: перед кроком ворога питаємо `squad.blockerAt(e.row, e.x)`;
  є блокувальник упритул → ворог не рухається, обмін ударами по `hitEvery`
- нова функція `bakeTrace(renderer, strokes, look): Texture` — випікає
  обведені гравцем штрихи в текстуру союзника (той самий принцип, що
  `procart.ts#bakeCatalogue`, тільки на рантайм-даних, не на каталозі)

### `src/controller/towerPanel.ts` — новий
Копія інтеракції `workshop.ts`, `readSockets()` спрощено до фіксованого
якоря (без `footOf`/`cx,cy`), межа тапу-поза-вежею — фіксований прямокутник
замість грід-математики.

### `src/controller/squadPanel.ts` — новий
Тап по **ряду** в зоні загону → вибір типу (мілі/ренж) → `tracePad.show(outline)`
з контуром відповідного силуету → `bakeTrace` → `squad.addAlly(kind, row, quality)`.
Ряд визначається через `lane.rowOf(y, ...)` — те саме, що використовує рух ворогів,
тому промахнутись рядом неможливо.

Два силуети союзників — нові дані в `data/allies.json` (та сама форма, що
`towerparts.json#parts`: `outline`, `size`, `cost`, `stats`), щоб `bakeTrace`
і полиця вибору працювали тим самим кодом, що вже є для деталей вежі.

### `src/controller/laneHud.ts` — новий
Дублює (не імпортує) невеликі хелпери `drawEnd`/`tally`/`penIcon` з
`hud.ts` — за YAGNI: 50 рядків, дублювання дешевше за абстракцію заради
одного додаткового споживача. Свій `SLOTS`: іконка каталогу турелей, іконка
«намалювати союзника», чорнило, життя, хвиля.

### `src/main.ts` — редагується (єдиний існуючий файл, який чіпаємо)
`const mode = new URLSearchParams(location.search).get('mode');` за тим
самим прикладом, що вже є `?debug`. `mode === 'lane'` → інший набір
конструкторів (`laneGame`/`towerPanel`/`squadPanel`/`laneHud` замість
`game`/`workshop`/`tools`/`hud`), той самий `app.init`/`paper`/`boil`.

### Крок 4b: переобведення деталі — ЗНЯТО на кроці 9

Нижче лишається як історія рішення: воно проіснувало від `85ac0d8` до кроку 9
і було прибрано разом з усім ink-шаром у `build.ts`.

**Чому не спрацювало.** Обіцянка була «деталь темнішає», а рендерилось `+4%`
розміру за рівень (`inkScale`) — за п'ять рівнів приріст 20%, якого оком не
видно. Гравець платив, обводив той самий контур п'ятий раз і не бачив різниці
ні в картинці, ні в цифрах (стати ніде не показувались). Плюс повторне
обведення того самого — це нудна робота, а не рішення.



Додано після того, як подивились референси — Grow Castle і Age of War. В обох
апгрейд **уже поставленого** юніта є основною віссю росту, а в нас вежа
впиралась у стелю, щойно заповнено пʼять сокетів: місця більше немає, а
сильнішати нема куди.

Тап по поставленій деталі → рамка з її ж контуром → рівень +1, стати ×1.15,
стеля 5 рівнів. Ціна росте з рівнем.

Два наслідки, які варто памʼятати:
- `inkMul(0) === 1.0` **рівно**, і селфчек це стереже. Лабіринт переобведення
  не використовує, тож його баланс лишається байт-у-байт тим самим.
- `canReink()` відмовляє деталям без статів. Заміряно: заготовка отримує
  +0.008 радіуса за рівень при ціні 12 чорнила — брати за це гроші означало б
  продавати порожнечу. `partAt()` такі деталі теж не бачить, щоб тап по тумбі
  не глушив закриття панелі.

Через це `RigPart` отримував `scale?: number`. На кроці 9 це поле видалено
разом з усім ink-шаром; замість нього з'явився `flip?: boolean`. `rigs.json`
не задає ні того, ні того, тому вороги, база й декор незмінні.

### Кроки 5 і 6 злиті

У первісному плані вони окремі. Насправді мілі й ренж живуть в одному `squad`,
і поділ циклу `update()` на два коміти лишив би половину непрацездатною.

**Що зроблено:** `laneGame.addAlly()`, `meleeHold()` у циклі оновлення,
вʼянення через `squad.tick()`, ренжові заводяться в `combat` тим самим
викликом, що й вежа.

**Що НЕ підтверджено:** чи мілі справді зупиняє ворога свого ряду. Остання
перевірка дала «ні», але в самому тесті була помилка — ворог зі швидкістю
1.5 клітинки/с за 4 секунди не встигав пройти 13.5 клітинок до блокувальника,
треба близько 9 секунд. Чи є під цією помилкою ще й баг у грі — невідомо.

**Місток із чужим ригом (знято на кроці 8).** Спершу `AllyDef.rig` вказував на
готовий риг `earling`, і це одразу вистрілило: `earling` намальований
**червоною** ручкою, тому союзник виходив точною копією ворога. Гра при цьому
працювала — юніт ставав у ряд, тримав, стріляв, — але грати було не можна, бо
на полі не видно, хто свій. Мораль на майбутнє: «тимчасово візьмемо готовий
арт» ламає не картинку, а правила читання поля, і селфчек такого не бачить.

### Крок 7: що вийшло інакше, ніж у плані

**Смуга HUD зверху, не знизу.** Низ ядра вже зайнятий полицею деталей вежі
(`towerPanel#shelfBand`), і сидіти там удвох нема як. У ландскейпі смуга
лишається збоку, як у лабіринті.

**Двокрокового вибору типу немає.** У плані було «тап по ряду → вибір
мілі/ренж». Зробили навпаки: тип обирається наперед іконкою на полях, тап по
ряду одразу відкриває рамку. Малювати доводиться під час хвилі, і зайве меню
між рішенням і олівцем коштувало б життів. Іконки — це самі `outline` з
`allies.json`, тому іконка не може розійтися з тим, що гравець обводитиме.

**Іконки каталогу турелей у смузі немає.** Вежа апгрейдиться тапом по самій
вежі (крок 4), і кнопка на полях була б другим входом у ті самі двері.

**Тап приймається по всій смузі рядів**, а не лише по коробці загону: союзник
однаково стає у свою колонку, зате в ряд заввишки з палець можна влучити.
Зона вежі виключена окремою умовою — `squadPanel` не покладається на те, що
`towerPanel` встиг забрати тап собі.

`squadPanel` заразом єдиний диспетчер вводу режиму (тап по нотатках, фінальна
записка) — та сама роль, що в `tools.ts` у лабіринті.

### Крок 8: `bakeTrace` — у бій іде намальоване

Функція живе не в `laneGame.ts`, як планувалось, а в `view/procart.ts` — і не
поруч із `bakeCatalogue`, а **всередині** нього: тіло циклу каталогу і є
випікання одного контуру, тому воно просто винесене в `bakeTrace(renderer,
outline, size, look)`, а `bakeCatalogue` тепер його кличе. Послідовність
викликів `penStroke` не змінилась, тож маски деталей лабіринту виходять ті самі.
Дві копії одного випікання розійшлися б виглядом, і намальоване гравцем
перестало б бути схожим на каталог, з якого воно й узялось.

Показ — через **звичайний риг з одної частини**, а не окремий спрайт: `laneGame`
збирає `RigDef` у коді (`traceRig`) і згодовує його `buildRig` разом із мапою з
одного запису. Через це союзник дихає, замахується на удар і реагує на хіт тим
самим кодом, що всі; жодного «рендеру союзників» у грі немає. Ручка (`pen` з
`allies.json`) лишилась — маска біла, і колір далі відповідає за те, хто на полі
свій. `AllyDef.rig` видалено разом із містком.

Текстура в кожного союзника **своя** — вона і є те, що він намалював, — тому
`dropAlly` її знищує (`tex.destroy(true)`). Спільні маски каталогу так знімати
не можна, тому риг і текстура лежать в одній мапі `allyArt`, а не поруч.

`addAlly(kind, row, quality, outline)`: без `outline` береться контур із даних —
тому виклик із консолі (`__td.laneGame.addAlly('melee', 1, 1)`) і далі працює й
дає ідеальний силует.

### Крок 9: рівні вежі й гілки замість переобведення

Скарга власника: «апгрейд башти не подобається, домальовані апгрейди інтуїтивно
незрозумілі й погано виглядають». Три причини, знайдені в коді:

1. **прев'ю не було взагалі** — полиця крихітних ескізів → абстрактна
   точка-сокет → модальна рамка → і лише потім видно результат;
2. **композицію ніхто не малював** — `freeSockets()` пускав будь-яку деталь у
   будь-яке кріплення, тому силуети, яких художник не бачив, були нормою;
3. **обидві осі росту невидимі** — стати рахувались із геометрії й ніде не
   показувались, а переобведення давало `+4%` розміру.

Рішення власника: лишити **і сокети, і рівні, і гілки** (механік має бути
багато), рамку обведення не чіпати, переобведення прибрати зовсім, гілка міняє
сокети + теги + має власну механіку.

**Рівень — це деталь-основа.** Окремої сутності «рівень» немає й не мало бути:
корінь складу і так деталь, тому `build.promote(id, partId)` просто міняє в
ньому `part`. Наслідки, які дісталися задарма: силует рівня обводиться тією
самою рамкою, печеться тим самим `bakeTrace`, а вищий рівень дає
далекобійність сам собою через `metrics().height` — без жодного нового стату.
Діти розсаджуються `reseat()` по нових кріпленнях; чиє кріплення зникло — той
знімається й **повертається назовні** (`dropped`), бо тихо втратити куплену
деталь гірше, ніж віддати за неї половину.

**Дані — окремий файл `data/towerTiers.json`**, який `main.ts` домішує в
каталог лише при `?mode=lane`. Дописати рівні в `towerparts.json` означало б,
що майстерня лабіринту раптом знає про Форт. Дерево `t1 → t2_fort/t2_arsenal →
t3_fort/t3_arsenal`, довільної форми: добрати гілку — це JSON, не код.

**Химера прибита типізацією.** `socketKinds` каже, які роди приймає кріплення;
несумісне під час перетягування навіть не малюється. Селфчек стереже головне
правило: зброя не мішається з оздобленням в одному кріпленні — саме з такого
кріплення й виходив ствол на даху. Деталі лабіринту `socketKinds` не мають, і
там фільтра не з'являється.

**`socketFlip`** дзеркалить деталь по x: без цього ствол у лівому кріпленні
Цитаделі дивився б у вежу. Дзеркалення живе на **спрайті**, а не на суглобі —
`rig.update()` щокадру скидає суглобу масштаб через `squash`, тому там воно б
не втрималось; заразом діти не перевертаються за батьком.

**Перки гілок, обидва без єдиного рядка в `combat.ts`:**
- **Форт — щит.** `advance()` витрачає заряд замість життя; заряди повні на
  кожній перерві між хвилями. Видно в смузі полів дужками перед рисочками
  життів — інакше гравець платив би за рівень і не бачив, за що.
- **Арсенал — другий ствол.** `combat` тримає скільки завгодно стрільців, тому
  другий ствол це **другий запис** (`TOWER_ID2 = -1`), шкода кожного `0.6`,
  відкат зсунутий на півперіод. Вежа б'є частіше й дрібніше. Ціль у них
  спільна — `pick()` детермінований, і обіцяти «по двох різних цілях» було б
  неправдою.

**Знайдений по ходу баг:** `combat.retune(id, null)` тихо нічого не робить,
тому вежа, яка після рівня втратила всю зброю, стріляла б далі старою
гарматою. Тепер точка заведення одна (`setGun`), і «немає гармати» означає
знятий запис, а не проігнорований виклик.

**Що стало видимим у панелі:**
- привид деталі **на вежі** під час перетягування — у клітинках світу, з
  піво́том і дзеркаленням, тобто саме там і саме такий, як стане;
- блок статів рукою біля вежі з **дельтою** на притягнутому кріпленні. Дельта
  міряється сухим прогоном: деталь ставиться, стати читаються, деталь
  знімається — без оплати й без перезбору рига;
- карточки на полиці більше не розтягуються в квадрат (`sketch` тримає
  пропорції) — через це вони й виглядали погано;
- спалах маркером над вежею, коли ввімкнулось комбо: вони працювали від
  кроку 4 і не давали жодного знака про себе.

**Тап-зона вежі — одне число (`towerReach`)**, а не по «1.5» у панелі й у
загоні: Цитадель зі стволами по боках із такої зони вилазила. Зона обрізана
передньою колонкою загону, бо на вузькому екрані `spriteScale` доходить до 1.8.

**Ліміт, який лишається:** при `spriteScale` 1.8 малюнок Цитаделі візуально
дотягується до зони загону. Тап-зона обрізана, тобто грати можна, але
картинка тісна. Міряти на 375×812 і, якщо тісно, звужувати силует t3, а не
розтягувати рівень — `laneLevel.towerX`/`squad.xLeft` тримають баланс руху.

- `npm run check` — 0 помилок після кожного кроку
- `npm test` — `lane.ts`, `squad.ts` і рівні вежі покриті в `tools/selfcheck.js`:
  геометрія рядів і зворотність `rowOf(rowY(r)) === r`, повний ряд, заміна
  найслабшого, `blockerAt` у правильному ряду; далі рівні — еталонні числа
  складу лабіринту (зняті з коду **до** видалення ink-шару й звірені на

  збите, відмова на перескок рівня, типізація кріплень, дзеркалення в
  `rigDef`, найширша вежа вміщається до колонки загону, плюс валідація
  `laneLevel.json` / `allies.json` / `towerTiers.json`
- Усі групи звірені мутацією: підміна колонок мілі/ренж, перейменування
  кріплення, знятий `socketFlip`, гілка в неіснуючий рівень, зброя на верху
